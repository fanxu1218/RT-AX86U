# localmod2-r7 DDNS-Go 多轮持续内存验证

本轮在固定原包的一小时、8 轮负载/空闲中，**未复现约 1.34 MiB 留存随轮次持续积累**。空闲低点有小幅波动，但最终静置后回到第一轮空闲低点附近；观察结果更符合首次扩容及容量留存/复用。这是有限窗口下的判断，不是对象级根因证明或长期无泄漏认证。

实际观测窗 **3601.015 秒**，完成 **3522 次 HTTPS 查询**（含恢复原监督脚本后的 3 次检查）、**4640 次额外完整网页读取**；**55 次 GC 的存活堆读数均不足 1 MiB**，堆目标均为 4 MiB。17 项专项检查通过，常驻 DDNS-Go、HTTPd/httpdb/skipd、UU 测试进程 PID 在观测窗内保持不变；没有通过重启清零内存。

- 后四轮空闲末值为 13772、13996、13832、13832 KiB，跨度 **224 KiB**，首末净增 **60 KiB**；描述性线性斜率为 1.6 KiB/轮，不应将其当作泄漏率或统计证明。
- 最终静置使目标 RSS 从第八轮末的 13832 KiB 再降至 **13544 KiB**，回收 **288 KiB**，比第一轮空闲末值低 **8 KiB**。没有出现每轮再次增加约 1.34 MiB 的模式。
- 相对两分钟预热末值仍留存 **1068 KiB（约 1.04 MiB）**；若采用 60 秒后首个周期样本作为起点，净增为 **1284 KiB（约 1.25 MiB）**。留存没有被“修成零”，关键证据是多轮后未持续放大，且静置能进一步回收。
- QEMU 原生映射相对两分钟预热末值净增 **3208 KiB**，其中绝大部分在首轮出现；第一轮空闲末至最终仅增 **204 KiB**。它与目标映射分开计量，不能将总 RSS 的增长全部归给 Go 存活对象。

没有复现足以修改固件或第三方原包的内存泄漏。修改仅限延长测试上下文期限、增加重复阶段与校验前的空闲基线、补齐可写映射及共存资源采集；为回归报告增加可选输出标签，保留历史记录。未加入定时重启、内存限额或人为 GC。生产镜像仍为 r7，SHA256 `989ce7d6f5863ca450dea0857bd483cb40757f6089113c9fcbdb51891704e677`。

## 对照方法

针对上轮禁用透明大页后仍有约 1372 KiB（1.34 MiB）目标 RSS 净增，本轮将同一个常驻 DDNS-Go 的观测窗延长至 3600 秒。使用原始软件中心包 1.29.0 的 UPX 压缩 ARM32 程序，二进制 SHA256 为 `9a6fb27190b1bbf7078ce89c1ae75db1567547e050cff42aa15b170f19ff2ddc`，没有用重编译版本替代。

先预热 120 秒，再执行 8 轮，每轮 120 秒网页加载、240 秒空闲，最后额外静置 600 秒。加载时每次约一秒的轮询迭代额外完整读取 5 次 DDNS-Go 页面并关闭 keepalive；每个阶段的实际完成次数均单独记录。阶段计时包含边界采样与校验开销，不把阶段长度等同于固定请求次数。

原厂认证 HTTPS 上的软件中心状态/版本查询全程继续，所有请求使用独立 ID，不自动重发。状态查询仅检查进程与监督运行时间；版本查询另起短命 `ddnsgo -v`，不是向常驻服务发送网页负载。原插件定时器继续运行。空闲阶段停掉周期性 DDNS-Go 网页读取，UU 心跳检查和软件中心查询继续；阶段边界的数据校验仍会读取一次网页。

采样每 20 秒进行，并在预热、加载、空闲结束时追加采样。**空闲末尾和最终静置基线先采样，之后才执行含网页读取的数据校验**；没有人为调用 GC、释放内存或重启服务来制造回落。八轮空闲末尾的设计时点为 8、14、20、26、32、38、44、50 分钟，最终基线为 60 分钟。

沿用 `QEMU_GUEST_BASE=0x100000000` 与 smaps 分离目标映射/QEMU 原生映射，验证 perf-map 地址落在宿主可执行映射。测试专用原生启动器仅对 DDNS-Go/QEMU 进程禁用透明大页，每个样本要求 `THP_enabled=0`、`AnonHugePages=0`。Go 参数保持 `gctrace=1,scavtrace=1`；没有更改 GOGC、GOMEMLIMIT、QEMU 翻译缓存上限或设置按内存重启。

新增每段可写目标映射的地址范围、虚拟大小、RSS、匿名页、私有脏页和交换量，并记录软件中心 HTTPd/httpdb/skipd、UU 测试进程的 PID、RSS 和 FD。软件中心、DDNS-Go 与 UU 在观测窗内均要求 PID 不变，避免后台重启掩盖增长。其他服务的 RSS 仍包含各自 QEMU 开销，不能直接解释为实机消耗。

## 入口与夹具校验

```sh
python3 build/check_memory.py --mode cycles-probe-no-thp
python3 build/check_memory.py --mode cycles-no-thp
python3 build/check_soak.py --smoke --label memory-cycles
```

以上检查按顺序运行，不能同时重建同一套共享测试程序或并发启动 VM。短预检为 90 秒、两轮缩短阶段，只验证阶段切换、基线采样、PID 及数据检查，不用于判定泄漏。正式运行准备与恢复开销不计入 3600 秒观测窗；JSON 的 `duration_seconds` 包含最终恢复等耗时，以最后一个观测样本的单调时钟读数核对实际观测窗。

夹具服务上下文期限改为按所选观测时长加准备/清理余量计算，以免原来的 30 分钟上下文截断一小时测试。结束后恢复原监督脚本，重新完成正常查询，再核对插件配置、原生数据库记录、原厂证书存档及 UU 合成持久化/临时数据。所有诊断修改均只作用于可丢弃 guest。

## 解释边界

Go 1.25 区分对象分配、运行时保留的地址空间和可复用的空闲 spans；空闲 spans 可以保留供后续堆或栈使用，也可能已归还操作系统。因而 RSS、保留容量与 GC 后存活对象不是同一个数值。这里借助多轮空闲基线、映射变化及 GC/scavenger 读数作趋势判断，**未取得原包的对象级 MemStats/heap/goroutine profile，不把某段匿名映射直接命名为某类 Go 对象**。[Go 1.25 MemStats 文档](https://pkg.go.dev/runtime@go1.25.0#MemStats)

上轮 1.34 MiB 的起点是 60 秒后的首个周期样本，末样本在完整数据校验后采集；本轮另以加载前与空闲末尾、校验前的基线为重点。两轮的净增量不是严格相同口径，不能逐页对账；上轮报告和原始样本保持原样。参见 [上轮分层排查](DDNS-Go内存排查说明.md)。

Go GC 日志以整数 MiB 向下取整，`0 MB` 只表示不足 1 MiB。RSS 为采样值，不能证明瞬时峰值或无限期无泄漏。观测结论限于无外部网卡、宿主工作区只读的 Linux 6.12.114/QEMU 10 测试环境、合成配置及网页/软件中心只读查询。UU 运行原厂控制流程及自有心跳进程，未使用真实 UU monitor、账号或游戏流量；未验证 WAN 提供商更新、原厂内核/NAND、实机或多天运行。本轮没有连接或刷写路由器。
