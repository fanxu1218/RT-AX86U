# 构建与发布校验

本轮版本统一定义在 `build/release_config.json`，当前构建候选为 localmod2-r9-r1；原 r9、r8 及历史交付保留。输出新文件，不覆盖旧镜像或历史 GitHub 标签/附件。原厂 rc、HTTPd、UU 页面、BusyBox、xtables、内核模块和启动区保留检查仍为必过项；六个移植程序的原厂版本另保留为回退程序，全局认证/TLS 库保持原厂字节。

## 使用入口

```sh
python3 build/check.py quick
python3 build/check.py dependencies
python3 build/check.py release
```

- `quick`：检查受管理 Python/Shell 源码，编译关键 C 文件；有本地固定 Zig 时检查 ARM ABI。另用宿主编译器执行真实归档边界和超时控制冒烟检查，不依赖路由器固件。
- `dependencies`：逐项验证 93 个固定输入的长度和 SHA256，并核对 Go/Node 版本。包括官方/软件中心/所选梅林映像、元数据、Zig、测试内核/initramfs、完整系统仿真 APK/模块、patchelf 来源及许可证文本。`dependencies.lock.json` 是本地已审查输入的可重复性记录，不等于厂商签名认证。不会自动更新版本或静默下载替代件。
- `release`：先执行以上检查，编译/组装新候选，执行原模型与原厂程序检查，回读 UBI/UBIFS 内容/权限/CRC，检查证书生成保存恢复、在线/真实 HND 插件、HTTPS 断连、中断恢复和损坏/低空间；最后在相同候选字节上重跑新增加固、状态与六轮并发共存检查。前后核对源码哈希；变化必须重新验证。

完整环境需要 macOS Virtualization.framework、已挂载的区分大小写构建卷和固定上游输入；历史对照还需要完整 Git 历史。源码附件不含 Git 数据、厂商底包或本地工具缓存。全部 VM 都使用独立输入/状态副本；真实第三方插件 VM 从只读封存目录运行，受控构建/早期模型使用可写专属副本并在收集有界结果前核对完整输入清单，组合加固分片由入口有界并发；旧检查器的编译与覆盖层准备仍按顺序执行，不支持任意并发运行检查器，也不得在流程校验期间修改其绑定源码。ARM64 Alpine 模型根目录使用 CPU 包装器；完整原厂根目录使用实际 ARM 帮助程序及 binfmt，两者分别记录边界。隔离、取消和底包差异检查见 `隔离分片与底包升级说明.md` 和 `构建模型隔离说明.md`。

## CI 与发布

`.github/workflows/check.yml` 在 push/PR 执行快速检查，只有仓库只读权限，关闭检出凭据持久化；checkout 固定为完整提交哈希。CI 不包含上游大文件及 macOS 虚拟化环境，不宣称完成镜像或实机验收。权限及固定哈希原则参见 [GitHub 官方安全参考](https://docs.github.com/en/actions/reference/security/secure-use)。

源码、报告完成审查并提交/同步后运行：

```sh
python3 build/publish_release.py
```

该入口要求工作目录干净、远端 main 与本地 HEAD 一致、完整 release gate 与源码哈希一致。源码包仅来自 Git 受管文件；不会打包下载缓存、测试磁盘、合成私钥目录或个人配置。生成附件清单后创建新的实验预发布，逐附件核对 GitHub 提供的长度和 SHA256，检查旧版发布正文/附件身份和 r7 注释标签未变。已存在同名发布时停止，不覆盖附件。

发布回执 `release_delivery.json` 作为后续单独提交，不改变预发布源码标签所指提交。完整流程没有路由器连接、备份或刷写步骤。

当前按用户安排交付本地成果，后续推送由用户操作；没有执行新的推送或发布。`local_delivery.json` 是最新候选的本地校验与移交记录，`release_delivery.json` 仍是历史 r8 回执，两者用途不同。手动推送、核对同一提交的 CI、可选创建预发布及单独提交真实发布回执的步骤见 `手动推送与发布步骤.md`。本地交付包不会改变受测固件或自动联网。

## 测试就绪与完整重跑

单 CPU 磁盘恢复夹具的 DDNS-Go 就绪曾接近旧约 4 秒轮询窗口；有界观测记录一次约 3.98 秒。测试改为 20 秒并记录实际耗时，不修改固件服务或自动重启策略。失败基础盘和全部中断场景重新执行。

调试时可用 `python3 build/check.py finalize` 核对同一输入流程的已通过报告、重新编译生产程序与镜像逐字节比较、检查脚本/页面生成结果及变更白名单。源码变化必须符合流程保存的输入清单，否则要求完整重跑。它只汇总证据，不代替执行用例。

本轮后来定位 TLS 输入阶段的可重试信号被当作 EOF，并修改生产适配库，因此最终重新执行完整 `release` 流程。输入阶段原厂 5 秒预算及旧版对照通过 `python3 build/check_tls_input.py --candidate` 单独验证，门禁也会调用此入口。

发布附件沿用历史版本的固定 ASCII 文件名（如 `HARDENING_NOTES.zh-CN.md`）；仓库和源码包仍保留中文路径与内容。发布脚本逐字节核对别名副本与原文，并在附件清单中记录原始路径；避免本次中文名上传端 404 的兼容性问题。

历史 r9 的完整门禁先在不变源码上通过，再补齐早期构建/模型的独立副本执行器。该后续变更仅涉及测试基础设施和发布说明：七项实际模型、独立 UBIFS 回读、篡改/链接/清单外输出及真实双 VM 取消对照重新执行，证书和在线控制器也通过新入口重跑。`finalize` 保存完整阶段报告哈希，仅允许准确列出的已审查测试文件变化，并重新编译生产程序、比较镜像回读字节。它不会把未执行的新用例算作通过。结构回读报告本身不是全部插件的运行验收汇总，六种固定插件的证据分别见 `real_plugin_tests.json` 和 `fancyss_tests.json`。历史 `health_tests.json` / `uu_recovery_tests.json` 等早期覆盖层报告不替代 r9；当前组合结果在 `hardening_tests.json` 的候选分片中。

## r9-r1 专项与恢复验证

新版软件中心的真实 1.9.50→1.9.60 迁移九项、发布前端函数七项、Fancyss/FRPC/PushPlus 组合 35 项和六个梅林组件服务 19 项均绑定 r9-r1 镜像。组件测试用完整 Cortex-A53 系统仿真与 Linux ARM32 兼容执行，覆盖实际 DHCP、SSH、UPnP/iptables、VPN TUN/PAM 和下载证书拒绝；不替代目标 4.1 内核/硬件验收。浏览器模拟界面报告独立标注。

构建时修复了发布包两处符号链接权限记录与 Linux inode 不一致的问题并重新构建。后续有三处测试文件修正：将新版 curl 与原厂数字地址行为分开作对照；加入三类原厂 SSH 密钥和 OpenVPN 单组件回退检查；按原厂 OpenVPN 的版本查询退出码及有界 RSA 测试密钥生成耗时修正夹具。受测固件字节没有随这些测试变动；已完成阶段哈希封存在恢复校验记录中，后续门禁逐项执行，最终 `finalize` 会重编译所有生产对象并对比回读。完整结果以当前 `release_gates.json` 为准，执行中不把已完成专项称为全部门禁通过。

本轮最终本地门禁已通过：170 项源码输入、93 个固定依赖、17 份绑定/关联报告。后续七项私有模型复测会重新生成日志和实时探测计数，八处报告替换均已核对新任务的不可变清单和原始串口日志；旧/新哈希与控制器来源记录在 `release_gates.json` 的 `resumed_validation.snapshot_origin.refreshed_reports`。最后重新编译全部生产程序并与候选回读比较一致，没有刷写或推送。
