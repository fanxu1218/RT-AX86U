# r9-r2 Fancyss 延迟与 DDNS-Go 内存归因

当前状态：定向预检完成，正式一小时双进程多轮观测正在运行，尚未计为完成。原 r9-r2 固件、完整门禁、此前一小时共存报告及 77 文件交付包均保留；没有刷机、访问路由器或推送 GitHub。

受测镜像 SHA256：`9ed280d8966b7a88e03f66ae74d87f7dacc760b2a173f50309b2c20372ef27a9`。DDNS-Go 插件包版本 1.29.0，实际 ARM32 程序 SHA256：`9a6fb27190b1bbf7078ce89c1ae75db1567547e050cff42aa15b170f19ff2ddc`。

## 区分哪些原因

- 仿真：主要 HTTPd、DDNS-Go 和六组件在完整 Cortex-A53 系统的 ARM32 兼容层执行。仅标注的 HTTPd 对照额外加入 QEMU-user；该层的 RSS 属于 HTTPd，不能把它算进直接执行的 DDNS-Go RSS。QEMU-system 宿主内存也不包含在客户机进程 RSS 中。
- 缓存及内核页策略：记录原生进程 smaps、匿名大页、私有脏页、PSS/LazyFree、线程、FD、GC 和 scavenger 日志；比较负载末值与随后空闲基线。
- 泄漏：使用同一 PID，观察多轮空闲基线及 GC 后存活堆是否持续上升。RSS 变化本身不足以证明泄漏或无泄漏，GC 日志整数 MB 刻度也不能排除更小的缓慢增长。

## Fancyss 耗时分段

对同一固定插件脚本做“原生 HTTPS → 额外 QEMU-user HTTPS → 原生 HTTPS”对照。每组同时比较真实 `ss_status.sh`、轻量控制回调、直接私有后端请求；记录连接、TLS、请求写出、首字节、公共脚本加载及实际回调 ID。全程客户端 10 秒，不重放超时请求。脚本仅加入临时阶段元数据，测试结束恢复原字节。

接口通过 `/_resp/$ID` 关联回调，响应 JSON 可以只有 `result`。采集器校验语义结果和脚本回调 ID，不要求响应回显 `id`。首次内部预检对这一合同的错误假设已修正，内部现场留在构建目录，不作为插件失败或本轮通过证据。

预检样本：直连后端 Fancyss 中位数约 3.93 秒，原生 HTTPS 约 4.16～4.27 秒，额外 QEMU-user HTTPS 约 4.93 秒。公共脚本加载约 3.5～3.8 秒；原生轻量回调约 0.4 秒，额外 QEMU-user 下约 2.1 秒。这些样本说明脚本准备和额外模拟均会贡献耗时，不能仅依据“等待响应头超时”认定 TLS 握手或后台回调丢失。

人为暂停 HTTPd 的两个对照单独标注：暂停 4 秒后约 7.94 秒完成；暂停 12 秒时客户端约 10.02 秒超时，恢复后后续查询正常。它们验证采集器能识别调度停顿，不是旧的自然偶发超时的重现，也不能用于宣称唯一根因已经确定。预检非人为故障请求未失败。

## DDNS-Go 双进程对照

主进程保留默认内核页策略。测试副本使用相同程序字节和配置种子，仅对该进程调用 `PR_SET_THP_DISABLE`；为避免与软件中心的 `pidof ddnsgo` 冲突，副本使用独立文件名、监听端口和临时配置路径。没有修改全局 THP 设置，未将诊断开关或 helper 放进固件。

两份进程均只启用 `GODEBUG=gctrace=1,scavtrace=1,gcpacertrace=1` 观测日志，保留原 GC 策略，不设置内存上限或定时重启。每轮对两进程交替、等量读取页面；空闲期不读取 DDNS-Go 页面，软件中心状态脚本只查 PID/perp 状态，UU/Fancyss 及其他组件继续共存。所有原插件配置、数据库、证书及 UU 测试数据定期核对。

计划：120 秒预热，六轮各 120 秒负载/300 秒空闲，最后 960 秒静置，共 3600 秒。两份 DDNS-Go 及共存进程在测量期间保持 PID 和启动时间不变。先取空闲末值，再做可能增加负载的检查。

短预检在默认进程看到 10～12 MiB 匿名大页，副本全程为零；末值 RSS 分别 17628/15204 KiB。两进程各观测到一次 GC，存活堆日志均为整数 0 MB。短窗口只证明这个测试内确有大页相关差异，不能把全部大页字节视为浪费，也不能据此认定一小时或实机没有泄漏。

两份进程的文件名、端口和地址布局不同，单个时点的 RSS 差额不能全部归于 THP；需要结合各自空闲期的大页变化、回收记录及跨轮基线。运行时保留页与精确存活对象也不能直接等同。

另外对当前候选和固定的官方底包做独立静态回读：从 UBI 静态卷 `filestruct_full.bin` 提取 `vmlinux.lz`，核对各块头与数据 CRC，再解出内核内嵌 IKCONFIG。两份启动卷和内核字节完全相同，配置为 Linux/arm64 4.1.52，明确 `# CONFIG_TRANSPARENT_HUGEPAGE is not set`。配置 SHA256 为 `3e873b04ea617659d07f6bd999c72239b5f0e85c63fa1bc777c1ee4bcdadcb90`。因此 Linux 6.12 测试中观察到的大页提升不适用于目标内核构建；这不等于实机 RSS 或回收性能已验收。来源与校验链见 `r9r2_diagnostic_kernel_tests.json`。

`/debug/pprof/heap?debug=1` 返回 307，未获得有效堆剖面；不能据此断言程序未编译 pprof。本轮使用运行时日志，存活对象精度有限。

## 隔离与复现

真实插件只在无外网网卡、宿主导出只读的临时 VM 执行。系统为 Linux 6.12，内层 640 MiB、外层 1024 MiB、单虚拟 CPU；目标设备的 4.1 内核、NAND、无线/WAN、实际 UU 账号、Fancyss 全局/透明代理及真实节点未验收。UU 使用原厂 NTP/下载/校验流程和自有工作进程，Xray 只走自有回环流量。

```sh
cd /Users/apple/Desktop/RT-AX86U
python3 analysis/r9r2_diagnostics/check.py --mode preflight
python3 analysis/r9r2_diagnostics/analyze.py --mode preflight
caffeinate -i python3 analysis/r9r2_diagnostics/check.py --mode cycles
python3 analysis/r9r2_diagnostics/analyze.py --mode cycles
python3 analysis/r9r2_diagnostics/kernel.py
```

需要原工作仓库的固定底包、区分大小写构建卷与本地工具链。新诊断报告绑定受测源码、生成转换、VM 清单、原始日志及镜像哈希，独立于历史 r7 内存报告和原 r9-r2 共存报告，不混计时长或替换历史证据。
