# RT-AX86U KoolCenter Alpha 3 固件静态分析

分析日期：2026-10-24。对象：`RT-AX86U_386.3_2_cferom_pureubi_koolcenter_alpha3.w`。

**结论：这是 2021 年编译的 ASUSWRT-Merlin 386.3_2 + KoolCenter Alpha 3 改版固件。公开 MD5 与内部 CRC 均匹配，系统内容可以解包；但组件年代较早，软件中心下载与初始化逻辑存在明确风险，不建议在今天直接作为长期联网主路由固件。**

这是对文件的静态检查，没有执行固件程序、连接路由器或刷机。校验通过不能证明没有漏洞、后门或运行故障。

## 2. 镜像结构与启动内容

以下偏移均是**文件内偏移**，不能当作路由器实际 Flash 分区地址直接写入。

| 文件偏移范围，右端不含 | 内容 | 说明 |
| --- | --- | --- |
| `0x000000–0x100000` | CFE-ROM / 启动区域，1 MiB | 含 CFE、`94908REF` 等标识 |
| `0x100000–0x140000` | 两个 UBI layout 块 | 卷表 |
| `0x140000–0x4c0000` | 卷 10：`filestruct_full.bin`，28 个块 | 设备树、CFE RAM、压缩内核 |
| `0x4c0000–0x4e0000` | 卷 1：`METADATA` | 提交状态及 `cferam.000` 元数据 |
| `0x4e0000–0x500000` | 卷 2：`METADATACOPY` | 元数据副本 |
| `0x500000–0x5660000` | 卷 0：`rootfs_ubifs`，651 个块 | UBIFS 根文件系统，autoresize |
| `0x5660000–0x5660014` | Broadcom 尾部，20 字节 | 整包 CRC、`0x4908` 芯片字段等 |

UBI 参数：擦除块 PEB 128 KiB、逻辑块 LEB 124 KiB、最小 I/O 2 KiB、数据区偏移 4 KiB。根文件系统采用 UBIFS v4，默认 zlib 压缩；并非 SquashFS。

`filestruct_full.bin` 已拆出以下内容：

| 内容 | 原始有效大小 |
| --- | --- |
| `94908.dtb` | 4,988 字节 |
| `94908REF.dtb` | 5,000 字节 |
| `cferam.000` | 400,380 字节 |
| `vmlinux.lz` | 3,062,058 字节 |

内核去掉 Broadcom 包装并进行 LZMA 解压后为 8,983,168 字节。设备树有四个 `arm,cortex-a53` CPU 节点，与 Broadcom BCM4908 平台特征相符；`wl.ko` 的 vermagic 明确为 `aarch64`。

根目录提取出 3,576 个普通文件及 515 个符号链接，普通文件合计 147,239,949 字节。ELF 中有 192 个 AArch64 文件、594 个 ARM32 文件，显示该固件混用 64 位内核/驱动与 32 位用户程序；安装插件时不能仅按“CPU 是 64 位”选择二进制。

原始 UBI 全卷提取工具会在提取完根卷后尝试把非 UBIFS 的 METADATA 当作文件系统，从而报告 `Wrong node type`。随后单独重建根卷再提取，退出码为 0，日志无提取错误；这项工具错误不是根文件系统损坏证据。

## 4. 已确认的风险与行为

### A. 联网长期使用：组件与固件基线过旧

固件停留在 2021 年构建。OpenSSL 1.1.1 系列已于 2023-09-11 结束公开支持。[OpenSSL 官方说明](https://openssl-library.org/post/2023-09-11-eol-111/)

华硕 RT-AX86U 官方支持页已列出 2026-04-17 的 `3.0.0.4.388_24436`，以及多轮较新的认证、输入验证和系统资源访问修复。此对比说明安全维护存在明显年代差距；不等于本报告已经逐项验证旧包存在其中所有漏洞。[华硕官方支持页](https://www.asus.com.cn/supportonly/rt-ax86u/helpdesk_bios/?model2Name=RT-AX86-Series-RT-AX86U-RT-AX86S)

本次没有把版本号自动映射成“已证实可利用”的 CVE 列表。

### B. 插件下载关闭证书验证，之后执行安装脚本

证据：`/rom/etc/koolshare/scripts/ks_app_install.sh`：

- 第 210–214 行拼接下载地址，使用 `wget ... --no-check-certificate`。
- 第 231–232 行比较下载包的 MD5 与传入值。
- 第 246 行解压插件包。
- 第 391–394 行赋予执行权限，用 `start-stop-daemon` 运行插件内 `install.sh`。

这一流程未在所检脚本中提供独立的包签名验证。关闭证书验证使下载连接无法验证服务器身份；MD5 不能替代来源认证。如果包和受信任的校验元数据一起被替换，或插件源失陷，下载校验就不能建立安全保障。仅能替换包而不能控制其预期 MD5 时，仍可能被该校验阻止。

安装脚本没有指定降权用户，处在路由器管理服务的权限链中，通常意味着 root 级执行；实际进程 UID 本次未在实机确认。

### C. 初始化会改写 HTTP 端口，并删除指定 DNS 配置

证据：`/usr/bin/jffsinit.sh`：

- 第 85–89 行：将 `http_lanport` 改成 `80`、提交 NVRAM 并重启 `httpd`。
- 第 92–93 行：清空 `/jffs/configs/dnsmasq.d/*`。
- 第 144 行：设置 `sc_url=https://rogsoft.ddnsto.com`。

影响：自定义 HTTP 管理端口可能被重置；写在该 DNS 目录内的自定义配置可能丢失。这里仅确认 HTTP 端口修改，不能由此断言 HTTPS 一定被关闭，或管理界面一定暴露到 WAN。

### D. 插件安装、卸载脚本有可见的实现问题

- 在线脚本第 150 行赋值 `KS_SCRIPT_PID`，第 151 行却检查 `KS_SCRIPT`；离线脚本第 178–179 行也有同类问题。局部代码没有正确检查刚获取的进程变量，并发安装保护可能失效。
- 在线脚本第 463 行的文件测试写成 `..._uninstall.sh]`，右方括号前缺空格。该分支可能报测试错误并跳过这种命名的卸载脚本；下一分支仍支持 `uninstall_插件名.sh`。

以上来自代码检查，没有在运行中的路由器重现。

### E. 软件中心复位后的服务恢复有已知问题

当前 `koolshare-reset` 第 15 行会杀掉 `skipd`，随后重新初始化并启动的 `perp` 配置没有启用 `skipd` 监管项，因此存在复位后配置服务未恢复的合理解释。发布方 Alpha 4 更新日志明确列出了修复 `koolshare-reset` 后 `skipd` 不启动的问题，表明该测试阶段存在已知可靠性缺陷。[发布方 Alpha 4 说明](https://fw.koolcenter.com/KoolCenter_Firmware/Alpha-4/)

## 5. 外联、认证与“后门”判断的边界

- 已确认的软件中心默认源是 `rogsoft.ddnsto.com`；新界面会从该源加载 `/koolcenter/app.json.js` 插件目录。
- 前端包含 KoolCenter、KoolDNS、DDNSTO 相关功能。页面将机型、MAC、局域网地址写入本地 JavaScript 上下文，部分代码会由 MAC 生成设备标识；这些事实不等于已经证实向外部上传原始 MAC。
- `ks_home_status.sh` 会读取已配置的 DDNSTO token、运行状态和 JFFS 使用量，通过本地 `127.0.0.1/_resp/...` 返回给界面；不能把这个本地返回过程直接称为外传。
- `httpdb` 包含认证处理和 `Kauth-*` 标记，以及 `127.0.0.1:3030` 反向代理目标字符串。后者不是确认的对外监听地址；没有实机监听表与认证测试，不能判断其 WAN 可达性或认证是否可绕过。
- 在普通文件中检查了完整 PEM 私钥块、常见账号/密钥路径，未检出完整 PEM 私钥；部分二进制含有通用 PEM 解析标记，不应误报为内置私钥。这不覆盖 DER 密钥、混淆凭据或所有硬编码认证逻辑。
- 没有对全部闭源二进制进行完整反编译，也没有做运行流量抓包，因此**不能凭此次静态分析宣称“无后门”，也没有足够证据将其定性为恶意固件**。

## 6. 使用与刷写判断

适合作为旧版软件中心结构研究、脚本分析和隔离测试样本。不建议作为今天长期联网主路由的首选。

若考虑实际刷写，需要先确认设备确为 RT-AX86U、当前固件版本、升级/降级限制及恢复方式。文件含 CFE-ROM 和 CFE RAM 内容，但实际升级程序是否写入启动区域，取决于更新器策略，不能只凭文件名断言“一定改 CFE”。不能将本文件直接套用到 RT-AX86U Pro，也不能由相似命名推断其他机型兼容。

纯 UBI 镜像不能当普通压缩包修改后直接刷回。重打包需要保持卷布局、启动文件结构、各层 CRC、尾部字段及设备升级器校验要求。此次没有修改或重打包原固件。

## 构建阶段补充：文件名大小写

2026-10-24 后续官改构建中发现，macOS 默认不区分大小写的卷会合并部分仅大小写不同的 netfilter/xtables 文件名。原始固件文件及直接针对镜像的 CRC/哈希检查不受影响；普通卷上的提取目录不能据此视为完整重打包输入。新候选镜像已在区分大小写的 APFS 构建卷上重新提取，并按原始 UBIFS 路径、内容和元数据完成回读核对。
